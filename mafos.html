Section 1: The Developer Workspace (Super Admin)

The developer platform serves as the master administration cockpit to monitor ecosystem data, modify global services, and orchestrate underlying tenant instances.[cite: 1]

1. Core Menu Architecture

  • a. The Dashboard: A visual interface tracking global platform services and system-wide asset onboarding registration health.[cite: 2, 3] This workspace displays metric cards and numerical graphs summarizing platform activities.[cite: 8]
  • b. Registration and Onboarding: The critical intake dashboard handling the primary configurations and onboarding routing workflows for vendors.[cite: 4, 10, 12]
  • c. Data Inflow and Outflow Monitoring & Analytical View: A localized streaming node monitoring and visualization deck handling platform analytics.[cite: 5]
  • d. Services Layer: The infrastructure configurations console controlling core microservices, system environment thresholds, and global security features.[cite: 6]

3. Lifecycle Validation and Registration Business Logic

  • External Application Route: If an entity applies externally via public web forms, clicking submit generates a profile but routes the record into a "Processing" status queue, displaying a tracking card allowing the applicant to monitor onboarding status.[cite: 37]
  • Developer Bypass Privilege: If the onboarding form is filled out directly by a Developer within this administration panel, the application bypasses all queues and automatically sets the vendor to fully onboarded upon click submission.[cite: 38]
  • Scope Requirement: All components defined within Section 1 are explicitly required for the core MVP launch baseline.[cite: 39]

Hard Limit Threshold Enforcements: The frontend application must enforce a maximum cap limit of exactly 3 Master Admins total per vendor tenant, inclusive of the pre-loaded default shell profile. 3. Activation Flow Constraints

  • Internal Authorization: When a Master Admin is directly registered inside the Vendor Services console, they bypass secondary reviews and activate instantly with no approval delay.[cite: 74]
  • Routed Portal Intake: If an individual signs up externally via the Platform or Global platform using a Vendor's Unique Routed ID, their account initializes in a locked state and must wait for explicit vendor responses to activate the profile. The profile remains functional-less until explicit approvals occur.[cite: 74, 75]

4. Public Fleet Exposure and Manager Asset Allocation Engine

  • Marketplace Lead Aggregation: All registered asset items, such as vehicles, tricycles/keke napeps, cars, or POS setups, populate public layouts.[cite: 76, 77] When public visitors search the global job opportunity or leasing marketplace, the system exposes the public profile page of the vendor to show total distributed assets versus total available assets ready for deployment.[cite: 77, 78]
  • Manager Allocation Engine Flow: The Vendor selects a quantity of unassigned available inventory stock from their pool and pushes ownership blocks to a Master Admin.[cite: 78]
    • UI Simulation Interaction: Vendor views total asset counts (e.g., Total Assets = 50 tricycles)[cite: 78]. They invoke an asset assignment modal, select an active manager profile (e.g., [Choose Manager: Abduljabbar]), define the vehicle configuration (e.g., Asset = tricycle), and define quantities (e.g., Numbers = 30)[cite: 79, 80, 81, 82].
    • Interlocking Modal Guard: The UI fires a confirmation modal: "30 tricycle will be assigned to Abduljabbar and will be ready for distribution, proceed?"[cite: 82].
    • Downstream Execution: On user confirmation, the data pipeline updates state targets and reflects instantly on the assigned master admin profile dashboard, displaying metrics for assigned assets versus assets distributed to drivers.[cite: 83]

5. Financial Insights and Accountability Grid

  • The workspace incorporates a financial metrics engine processing tracking cycles across daily, weekly, and monthly payment flows.[cite: 85]
  • The Vendor UI has comprehensive monitoring blocks tracing what balances remain left in the field, what values are safely settled, and exact values expected in upcoming pipeline periods.[cite: 86]

📌 Critical Core UX Architecture Rule (The Pinned Account Header):
To ensure collection efficiency and remove friction, all corporate bank account numbers designated for driver payment deposits must be rendered inside a prominent, high-contrast, sticky header element. This payment box remains permanently fixed to the absolute top of the viewport frame. Even when a driver navigates across separate menu sections, this corporate bank account info elements remain rendered at top of the screen at all times.[cite: 138]
